# Ordo Web

Responsive Next.js client for Ordo. In the Cloudflare design it is built as a static export (`output: 'export'`) and served by the same Worker that serves the API under `/api`, so the browser talks to one origin and the session cookie stays first-party.

**Implementation status:** `npm run build` produces a static export in `apps/web/out`, which the Worker under `wrangler dev` serves on `127.0.0.1:8788` beside `/api`. For development, `next dev` on `127.0.0.1:3358` proxies `/api/*` to that Worker. Sign-in is code only. Nothing is hosted yet; hosting is Phase 3. Delivery follows coordinated-development. Mobile native work follows web using the agreed React Native/Expo direction with iOS priority; this browser app is not the native mobile deliverable.

## Run

From the repository root, with Node 22 selected:

```bash
npm ci
npm run dev
```

Open http://127.0.0.1:3358. The root `npm run dev` applies local D1 migrations, then starts the Worker (`wrangler dev` on 8788) and `next dev` on 3358 together; see [local development](../../docs/LOCAL-DEVELOPMENT.md) for the details and for running them separately. `npm run dev --workspace @ordo/web` starts only the web dev server and expects the Worker to be running. `ORDO_API_URL` optionally overrides the Worker origin for the dev proxy (default `http://127.0.0.1:8788`); it is not a browser-exposed variable.

## Static export and same-origin `/api`

`next.config.ts` is phase-aware. Under `next dev` it adds a `/api/:path*` rewrite to the same path on the Worker, which maps `/api/*` to the API's `/v1/*` exactly as it does for the export. Every other phase (including `npm run build`) sets `output: 'export'` and has no rewrites, so the build is plain HTML, CSS and client JavaScript in `apps/web/out`; there are no route handlers, server actions, or request-time `headers()`/`cookies()`. The export is a single page with no client-side routes, so the Worker's `404-page` asset handling is sufficient.

The browser client always calls `/api/...` relative to the page's own origin (`createClient('/api')`). There is no absolute API URL in browser code and no `NEXT_PUBLIC_` API variable. To check the export as hosted Ordo will serve it, run `npm run build --workspace @ordo/web`, start `npm run dev`, and open `http://127.0.0.1:8788`. `next start` does not apply to a static export.

Sign in or create an account with an email address or Ghana phone number and a six-digit code. Locally, with no Gatekeeper values, the code is printed in the `wrangler dev` terminal. The code field keeps only digits, so a pasted `658 659`, `658-659` or a code with a stray space or line break still works, and Enter submits from the code or name field. A short code shows a plain error under the field instead of a browser tooltip. The form does not auto-submit at six digits, so a new account can still add its optional name. There is no password sign-in. Start empty or explicitly load the fictional examples. Fixtures are added only to the signed-in account.

## Working flows

- Code sign-in and logout; no passwords exist and none are kept in browser storage.
- Workspaces with distinct colors, project creation/filtering, global views, and scoped task/note capture.
- Project detail has five tabs: **Overview** (open, overdue, waiting and note counts; overdue tasks as blockers; the next open tasks; Waiting On with who; the three most recent notes), **Tasks**, **Notes**, **Conversations** (the project's recordings, emails and transcripts, including captures filed elsewhere whose saved tasks went to this project, each with its AI summary when processed and the tasks created from it, or Process with AI) and **Drafts** (see AI capture below). Arrow keys, Home and End move between tabs. Above the tabs, Add task, Add note, Record and Upload all land in that project.
- A star favourites a project (`favorite` on the project, saved with `PATCH /projects/:id`). Favourites come first in the sidebar's project list and in Pick up where you left off, and the project header has the same star.
- Settings starts with **Your name**, saved with `PATCH /auth/me` (empty clears it; a phone number or email is refused with a plain message). My Day's greeting and the avatar use it. With no name the greeting has no name, the avatar shows a person icon instead of letters, and the profile reads "Your account": contact details are never shown.
- Tasks, nested subtasks, explicit completion, status/priority/date editing, and archive. Parent completion does not complete children. Tasks with active children cannot be archived until those children are addressed.
- My Day greets the user by first name with a time-of-day greeting (no name when the display name is missing, the API's placeholder, or looks like a phone number or email: contact details are never shown as a name) and today's date in their timezone (default Africa/Accra), a one-line summary, and five count chips (Today, Overdue, Upcoming over seven days, Waiting On, Inbox). Its list runs Due now (a timed due or follow-up moment today that has arrived), Overdue, Today, a three-item Waiting On preview, then undated tasks. This is in-app only: there are no browser notifications and no automatic status changes.
- Every task list starts with an inline composer (type a title and press Enter) that uses the view's defaults: My Day → due today, Inbox → no project, Upcoming → due on the chosen day (tomorrow by default), Waiting On → status Waiting.
- Inbox frames unsorted tasks and notes as triage. Upcoming groups the next seven local days ("Tomorrow", "Friday 23 Oct"), shows each item as Due or Follow up with its time, and offers to plan on empty days. Waiting On lists Waiting-status tasks with who they wait on, the follow-up date and time (passed follow-ups highlighted), and the responsible person.
- Task detail moves a top-level task under **Where it lives** (workspace, then project, or the Personal or Workspace Inbox); its subtasks move with it, the panel says how many, and the list updates without a reload. A subtask says to move its parent instead.
- Task detail edits due and follow-up dates with optional times (clearing a date clears its time in the same save), plus Responsible and Waiting on names, with suggestions from names already used. Only changed fields are sent. Rows show times and "Waiting on <name>" everywhere.
- Rich notes stored as Markdown text in `body` (existing plain-text notes are already valid). Write mode is a textarea with a formatting toolbar (Heading, Bulleted list, Numbered list, Checklist, Bold, Italic, Link; arrow keys move along it) and shortcuts ⌘/Ctrl+B, I and K; Enter continues a list and Enter on an empty item ends it. Read mode, the default for a note with text, shows the formatting, and checklist items tick in place, which autosaves. `lib/markdown.ts` parses the supported subset into plain data and `components/rich-note.tsx` renders it as React elements: note text is never rendered as HTML (no `dangerouslySetInnerHTML`), raw HTML stays visible as text, and only `http`, `https` and `mailto` links become links, opened in a new tab with `rel="noopener noreferrer"`; any other link stays as the text typed. The editor and parser load only when a note opens (`next/dynamic`), so My Day's first load does not include them; once the service worker is installed they are fetched at idle so notes open offline too. Note cards show a plain preview without the marks.
- Note lists (`/home`, `/notes`) carry each note's `preview` (its first 280 characters) and `bodyLength`, not its body; cards add "…" when the preview is only the start. Opening a note fetches `GET /notes/:id` behind a short "Opening…" state, and only then shows read mode or the editor, so no edit or checklist tick can start from a preview (`lib/open-note.ts`, `components/note-loader.tsx`). Each opened note's full body is kept per account in this browser (`@ordo/client/note-bodies`, the 50 most recent), refreshed on every save, so it stays readable offline as a read-only copy; a note never opened here shows its preview and "Open online to read the whole note."
- Notes autosave with debouncing, sequential revision handling, and close protection. The note pane shows one truthful state: Unsaved changes (Save now is the only active action), Saving, Saved at a time, Offline (not saved yet; saves again when the browser is back online), or Not saved (Try again). The footer says typed notes aren't sent to any AI service, and voice notes are transcribed by the provider chosen in Settings without keeping the recording. Conflicts preserve the current editor text for copying/retry; automatic merge is not implemented. A note made from a recording, an email or a transcript says so on its card and in the editor (`source`, set once at creation).
- **Upload Transcript** on My Day (hint "Or paste an email") and the project's Upload open one dialog with Transcript and Email modes. Paste the text, or choose a `.txt`, `.md`, `.vtt` or `.srt` file: the browser reads it locally (for `.vtt`/`.srt`, the header, cue numbers, timestamps and tags are removed; `<v Name>` becomes "Name: ") and only the text is sent. An email's Subject line, or a file's name, suggests the title. Choose the workspace and project, check or edit the text, and save it as a note with `source` `email` or `transcript`. Over 100,000 characters it says so and does not save. Nothing goes to AI; the dialog says extraction comes later.
- **AI capture** (release slice 2) runs only when you choose **Process with AI**: on a note in the editor (highlighted for recordings, emails and transcripts), from a conversation, or with the **AI Capture** tile, which brings in a capture and processes it once saved. Choose the workspace (only its project names, descriptions and other names go with the text) and optionally the project, or let Ordo suggest one. Processing shows progress and can be cancelled. The review screen groups the suggestions as Summary, Suggested destination, Tasks, Follow-ups and Drafts: each can be unticked, edited (every task field), removed, merged into another task, or put somewhere else; a low-confidence destination stays unassigned (Choose…) until you pick one. **Save selected** or **Save all** creates them in one batch linked to the note, then lists what was created with links. If AI is unavailable or fails, the capture is untouched and **Process later** leaves it marked *Not processed* on its card and in the editor (from the note's `latestCaptureStatus`, `pending` or `failed`). Tasks from a capture say **From capture** with a link to the source note. The project **Drafts** tab lists drafts with **Copy** (recipient, subject and text to the clipboard) and **Mark used**; Ordo never sends them. My Day shows the three most recent conversations. Project settings (the gear beside the star) edit the description and up to ten other names used to route captures. Settings › AI capture chooses **Built-in AI** (Workers AI, the default), **OpenAI (your key)** or **Anthropic (your key)**; capture buttons never name a vendor or price. The logic is in `lib/capture-review.ts` and `lib/capture.ts`; the screens in `components/capture-flow.tsx`, `components/conversations-drafts.tsx`, `components/ai-settings.tsx` and `components/project-settings.tsx`.
- `⌘K` / `Ctrl+K` searches authorized tasks, note bodies, and projects through the server full-text search endpoint.
- Responsive phone-browser layout, navigation drawer, and keyboard-accessible native dialogs.

## Local capture and honest offline limits

New tasks are first written to an account-keyed localStorage queue with a stable idempotency key. Successful server acknowledgment removes the queue record. Network/storage/validation failures remain visible. A new capture during an in-flight successful sync triggers another drain. Queues are never sent under a different displayed account: client write preconditions and server ownership checks enforce that boundary.

The current-account pointer and a last-loaded account snapshot are cached for an already loaded client. Logout clears the pointer and visible snapshot; unsynced task captures remain stored under the original account and require signing in as that account again. A 401 or account mismatch clears the active view. Browser data is device-local and should not be used on a shared device without considering local browser access.

## Read-your-writes bookmark (`X-Ordo-Bookmark`)

The Worker opens a D1 Sessions API session from the request's `X-Ordo-Bookmark` and returns the session's latest bookmark in the same header. The shared client (`packages/client`) keeps the newest value per account, in memory and in localStorage under `ordo.bookmark.v1:<account>` beside the task queue, and sends it on that account's next request. D1 documents bookmarks as lexicographically sortable from oldest to newest ([D1 bookmarks](https://developers.cloudflare.com/d1/reference/time-travel/#bookmarks)), so when responses arrive out of order the client keeps the larger value rather than the last to arrive. A bookmark received before sign-in is held in memory only and carried over to the account that signs in. Sign-out clears that account's bookmark, even if the sign-out request fails; other accounts' bookmarks are untouched. Storage failures are ignored, because a missing bookmark only means a read may come from an older replica.

**Opening offline.** The built export registers a service worker (`public/sw.js`, registered by `lib/service-worker.ts`) that keeps the app's page, scripts, styles and icons, so Ordo opens with no connection. It never answers or stores `/api/*`: account data offline is the last snapshot this browser loaded, kept in localStorage as above. Navigations are network-first (the stored page is refreshed each time), content-hashed `/_next/static/` files are cache-first, and the page hands the worker the build files it has loaded so lazily loaded chunks open offline too. When offline, or when the API can't be reached and the saved snapshot is shown, a banner says so and Ordo is read-only apart from quick task capture, which still queues on the device and syncs on reconnect. Completing or editing tasks, notes, favourites, Settings, search, recording and imports say they need a connection; the task and note panels open as read-only copies. `next dev` never registers the worker. Only task creation is queued; task edits, workspaces/projects, and notes require the API. Note text is retained in the open editor after a failure and warns on closing/unloading; it is not a durable offline note queue. A full multi-device sync protocol and conflict resolution UI remain later work.

Settings selects **Built-in transcription**, which is Workers AI Whisper on Ordo's hosting and the default (Cloudflare is named only in its detail line, never the label), or **OpenAI (your key)**, an account-owned OpenAI key; each shows its cost and where audio goes. The recorder and the Record card name no vendor or price; the recorder carries only the neutral privacy line. With a ready provider, Record captures microphone audio into memory; Stop transcribes it and discards the audio. Only the transcript can be explicitly saved as a note. There is no audio file picker, recording history, playback, or audio persistence. When the selected provider is not ready (Workers AI off on this server, which is always the case under `npm run dev`, or OpenAI without a saved key), the Record card reads "Set up in Settings" and opens a recorder that says why and offers Open Settings, without requesting microphone access. Transcription failures are shown in the API's own words, for example when today's free Workers AI allowance is used up; see [audio setup](../../docs/AUDIO-SETUP.md). Record stays "Coming soon" only when audio settings could not be loaded. A voice note is saved to the current project (or workspace) with `source` `recording`. Light, Dark, and System themes are supported.

## Checks

From the repository root:

```bash
npm run typecheck --workspace @ordo/web
npm run build --workspace @ordo/web
npm run test --workspace @ordo/client
npm run test --workspace @ordo/web
```

The shared-client tests cover bookmark store-and-forward (header absent, latest value forwarded, an older bookmark arriving late, reload, per-account separation, sign-in carry-over, sign-out clearing, unavailable storage), account isolation, idempotency preservation, storage failure, authenticated mutation preconditions, session-change propagation, and an autosave regression for edits made during a slow request. The web tests cover the pure view logic in `lib/views.ts`: the greeting, local-timezone clock, My Day sections and counts, seven-day grouping across month and year ends, Waiting On ordering, name suggestions, the project Overview, favourites ordering, the name rule, avatar initials and note source labels; `lib/import-text.ts`: WebVTT/SubRip text extraction, accepted files and suggested titles; `lib/service-worker.ts` and `public/sw.js` run against a fake cache and network (API requests are never answered or stored, and an installed worker opens the app offline); `lib/markdown.ts`: parsing, unsafe links and raw HTML kept as text, ticking in place, toolbar line formats, bold/italic wrapping, link insertion and list continuation; and `lib/sign-in-code.ts`: sign-in code normalising (spaces, dashes, line breaks, non-breaking and zero-width characters, full-width and Arabic-Indic digits) and the short-code message. Browser verification is recorded separately (Phase 2 screenshots on `wrangler dev` are in `design/evidence/cf-phase-2/`; the everyday-core finish journeys are in `design/evidence/everyday-core-finish/`); compilation alone does not prove user journeys.

## Appearance

Use the sun/moon icon in the top bar or sign-in screen to switch between Light and Dark. The choice is saved in this browser. Before an explicit choice, appearance follows the operating system. Both themes retain orange accents and workspace colors. CSS light-dark() requires a current browser.
